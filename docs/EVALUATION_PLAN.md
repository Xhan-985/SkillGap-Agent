> SkillGap Agent ｜ Phase 1 交付物 ｜ 本版在 Phase 0 基础上新增 E5 数据质量评测（变更记录见 DECISION_LOG.md）
> 铁律：**没有评估用例、评分规则、阈值、回归历史与失败分诊的模型变更，不允许进入主干**——评估是本项目的差异化支柱之一（研究中无任何竞品/开源项目做此事）。

## 1. 评估总体设计

### 1.1 评估单元（Eval Unit）定义

| 评测 | 评估单元 | 主证据 |
|---|---|---|
| E1 技能抽取 | 一条 JD 的一次抽取结果（技能集合 + 重要度 + 证据片段） | 标注技能集合（ground truth）vs 模型抽取 |
| E2 岗位匹配 | 一次（候选人画像 × JD）的打分 | 人工匹配分 vs 系统分 |
| E3 推荐质量 | 一份 ROI 排序建议（给定画像 + 时间预算） | 人工相关性排序 vs 系统排序 + LLM-as-judge 评分 |
| E4 解释质量（Phase 8+，Agent/RAG 引入后） | 一条解释文本 | 引用真实性（可核查）+ 事实一致性 rubric |
| **E5 数据质量（Phase 1 新增，MVP）** | 一次导入/ingest/贡献批次 + 定期全库扫描 | 指标值 vs 阈值 + 人工抽查记录 |

E1 属 LLM 输出评测；E2/E3 主要是**确定性系统评测**（分数由公式计算，评测的是公式设计而非模型）；E4 属检索增强评测（检索命中与答案引用分离评分）；**E5 使项目不只是"AI 应用"，同时具备数据工程能力证明（需求第二十六节）**。

### 1.2 使用意图与红线

- 评测结果映射的决策：**合并门槛（CI 阻断）+ Prompt/模型变更依据 + 回滚依据**
- 红线（承规划文档第二十节）：所有比例/相关系数基于真实标注数据计算；**LLM 不得参与 E1/E2/E3 的指标计算**（E3 的 LLM-as-judge 仅对解释文本打分，且 rubric 固定）

## 2. E1：JD 技能抽取评测

### 2.1 标注集

| 项 | 规格 |
|---|---|
| 规模 | **50-100 条 JD**（从 Demo Dataset 抽样，覆盖全部岗位类别与城市切片） |
| 标注内容 | 每条 JD 的 ground truth 技能集合（含 must_have/nice_to_have） |
| 标注流程 | 人工逐条标注 → 抽样交叉复核（20% 双标，计算标注一致性 Cohen's κ）→ 冻结为 v1 |
| 防污染 | 标注 JD 与 Prompt few-shot 示例**严格分离**；评测集不入 LLM 上下文 |

### 2.2 指标与判定规则

| 指标 | 计算 | 说明 |
|---|---|---|
| Precision | \|抽取∩标注\| / \|抽取\| | 误报（抽出没要求的技能） |
| Recall | \|抽取∩标注\| / \|标注\| | 漏报 |
| F1 | 调和平均 | micro 为主，macro 辅助（低频技能不隐身） |
| 重要度准确率 | must_have 分类正确率 | 单独报告 |
| 证据可溯率 | evidence_text 在 JD 原文中可定位 | 100% 硬要求（字符串定位校验，纯程序判定） |

匹配判定：抽取技能经 alias 表归一后与标注集合比对（防止别名误判为错误）。

### 2.3 阈值（预声明，跑分前冻结）

| 指标 | Pass | Warn | Block |
|---|---|---|---|
| F1 (micro) | ≥ 0.85 | 0.75-0.85 | < 0.75 |
| Recall | ≥ 0.85 | 0.75-0.85 | < 0.75（漏报比误报伤害大——用户缺口被低估） |
| 证据可溯率 | 100% | — | < 100% |
| 标注一致性 κ | ≥ 0.75（低于则先修标注规范再评测） | — | — |

样本量报告：每次跑分附 N；F1 差异 < 3% 视为噪声级变化，不作为合并依据（小样本显著性纪律）。

## 3. E2：岗位匹配评测

### 3.1 标注集

| 项 | 规格 |
|---|---|
| 规模 | **20-30 个（候选人画像, JD）对** |
| 画像构成 | 3-5 个差异化画像（强 RAG 弱工程 / 全栈均衡 / 新手缺 Agent 等，含合成画像） |
| 标注内容 | 人工匹配分（0-100）+ 强/弱/缺失技能三组标注 |
| 标注者 | 用户本人 + 若干同学（不同背景，检验一致性） |

### 3.2 指标

| 指标 | 计算 | Pass / Warn / Block |
|---|---|---|
| **Precision / Recall / F1**（技能三组分类） | 系统判定（Strong/Weak/Missing）vs 人工标注三组：P=\|交集\|/\|系统判定\|、R=\|交集\|/\|标注\|、F1=调和平均；micro 为主，**Missing 组单独主报**（缺口判定是核心输出），macro 辅助（低频组不隐身）（需求第二十五节指定指标，2026-08-31 评审 H8 补齐） | F1 ≥ 0.7 / 0.5-0.7 / < 0.5 |
| Spearman ρ（总分 vs 人工分，Correlation） | 排序相关性 | ≥ 0.7 / 0.5-0.7 / < 0.5 |
| MAE | 分数绝对误差 | ≤ 12 / 12-20 / > 20 |
| 强弱缺失命中率 | 三组技能与人工标注的 Jaccard | ≥ 0.7 / 0.5-0.7 / < 0.5 |
| 单调性检查 | 画像能力提升 → 分数不下降 | 100%（纯函数单测，确定性层专属） |

### 3.3 附加：对抗性用例（边界）

- 技能仅"裸声明"（低 confidence）→ 分数应低于有证据技能
- JD 要求与画像完全无关 → 分数应显著低
- 别名变体 JD（LangChain vs LangChain.js）→ 匹配结果一致（归一化正确性）

## 4. E3：推荐质量评测

### 4.1 评测设计

| 维度 | 方法 | 判定 |
|---|---|---|
| 排序质量 | 人工对 Top-5 建议排序 vs 系统排序 → nDCG@5 | ≥ 0.7 / 0.5-0.7 / < 0.5 |
| 数值正确性 | Potential Gain 抽样手工重算公式 | 100%（纯函数单测覆盖） |
| 解释合理性 | LLM-as-judge（固定 rubric：是否引用了真实频率/缺口/成本，是否无幻觉），5 点量表 | 平均 ≥ 4.0 / 3.0-4.0 / < 3.0 |
| 引用真实性 | 解释中出现的百分比与数据库 snapshot 比对 | 100% 一致（程序判定） |

### 4.2 LLM-as-judge 控制

- Rubric 固定并版本化；judge 模型与被测生成模型**不同源**（降低自评偏置）
- 每次变更后抽 10 条人工复核 judge 打分（judge 漂移检查）
- judge 评分只作 Warn/参考级信号，**不作 Block 依据**（数值正确性才是硬门）

## 5. E5：数据质量评测（Phase 1 新增）

### 5.1 指标定义（对应 DATA_PIPELINE 门禁 G1-G5）

| 指标 | 计算 | 阈值（Pass / Warn / Block） | 采集时机 |
|---|---|---|---|
| Duplicate Rate | 重复拒绝数 / 提交总数（按批次） | ≤10% / 10-25% / >25%（过高说明来源高度重叠，需调整采集策略） | 每次导入/ingest/贡献 |
| Missing Field Rate | 缺来源九字段记录数 / 总数 | 0% / — / >0%（DB 约束兜底，出现即 Block） | 定期全库扫描 |
| PII Detection | ①规则命中率（监控脱敏工作量）；②**漏检率**：人工抽样 N≥50 条已入库数据，人工标记 vs 规则结果 | 漏检率 0% / <2% / ≥2%（触发规则版本升级 + 存量重扫） | 每月抽样 + 每次规则变更 |
| Invalid JD Rate | quarantine+reject 数 / 提交总数 | ≤5% / 5-15% / >15% | 每批次 |
| Skill Extraction Error Rate | extraction_failed 数 / 抽取尝试总数 | ≤3% / 3-8% / >8% | 每批次 |

### 5.2 报告与回归

- 每次导入/ingest 批次自动产出质量报告（API `GET /api/quality/report` 聚合视图）；指标入库进回归历史（时间序列）
- PII 漏检样本 → 转入正则规则测试用例（case promotion，同 E1 坏例政策）
- E5 与 E1 联动纪律：Skill Extraction Error Rate 突增时先查 E1（Prompt/模型变更）再查数据分布漂移（新源引入）

## 6. 版本化与回归历史

| 输入 | 版本化要求 |
|---|---|
| Prompt | 版本号 + 变更记录（每条评测结果关联 prompt_version） |
| 模型 | provider + model 名 + 参数 |
| 评测集 | dataset_version（v1 冻结后新增用例进入 v2，不静默修改 v1） |
| 评分器 | scoring_version（公式改动 = 新版本 + 全量重跑） |
| 词表 | taxonomy_version（与评测集一致性由 CI 检查） |
| 结果 | 每次评测入库：全部指标 + 版本三元组（prompt, model, dataset）+ 环境 |

回归历史的最小呈现：时间序列表（每次 CI 评测一行），支持回答"这次改动让什么变好了/变坏了"。

## 7. 失败分诊（Failure Triage）

| 分诊类别 | 处置 |
|---|---|
| Blocker（指标跌破 Block 线） | 阻断合并，定位原因（Prompt/Schema/词表/公式）后重测 |
| 可接受回归（某切片下降但总量达标） | 记录豁免理由 + 复查触发条件（带有效期） |
| Flaky（LLM 输出方差） | 同版本重跑 3 次取中位；方差写入报告 |
| 数据问题（标注错误） | 修标注 → dataset_version +1 → 重跑全部 |
| 覆盖缺口（无对应用例） | 生产/用户反馈中的坏例 → 转为回归用例（case promotion 政策） |

## 8. 评测执行与 CI 集成

```
GitHub Actions 流水线：
  PR:    确定性层全量单测 + E2 单调性检查 + 评测集抽样（快速反馈，<5min）
  main:  E1-E3 全量评测 + 结果入库 + 与上一版本对比报告
  发布:  全量评测 + 阈值门禁（Block 即失败）
```

本地命令（设计冻结于 Phase 1）：评测集加载 → 执行 → 指标计算 → Markdown 报告（指标表 + 版本三元组 + 与上次差异）。

## 9. 诚实边界（本次研究导出的额外纪律）

1. 评测集规模（50-100 JD / 20-30 对）只能支撑**相对比较**（版本间回归），不支持绝对能力宣称——文档与 README 中不得写"准确率 85%"这类绝对宣传语，必须附 N 与版本
2. 中文技能抽取无现成公开标注基准（开源研究结论），因此本项目评测集本身是可开源贡献的资产
3. E4（Agent/RAG 评测）在 Phase 8 设计，届时引用 RAGAS/DeepEval 思路做检索与答案分离评分（工具可借用，标注自建）
